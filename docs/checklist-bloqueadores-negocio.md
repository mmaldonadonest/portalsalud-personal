Consolidado a partir de `js-version/CHECKLIST_BLOQUEADORES.md` (proyecto "Salud Ocupacional V2", Node/React/Postgres, que se decidió no continuar como sistema aparte — ver plan de integración en la sesión del 2026-08-10). Ese análisis se hizo directamente sobre los 10 archivos Excel reales del área de Salud Ocupacional (`EXAMEN MEDICO.xlsx`, `REPORTE MORBILIDAD.xlsm` y sus reportes fuente), independientemente del portal legacy PHP y del portal Java actual — por eso sigue siendo válido como insumo de negocio aunque el stack técnico que lo originó ya no se use.

**Propósito de este documento**: ser la fuente única de qué decisiones de negocio siguen pendientes con Médico Jefe / Gerente SO / RRHH / Admin IT antes de construir en Java cualquier funcionalidad nueva de Salud Ocupacional (dashboard de morbilidad, antidoping, accidentes de trabajo, maternidad, restricciones médicas, etc.). Estado al copiarse (2026-08-10, según `js-version/CHECKLIST_BLOQUEADORES.md`): 4 de 17 puntos resueltos, el resto abiertos o parciales.

## Resueltos

- **#1 — Contenido completo de `EXAMEN MEDICO.xlsx`**: el archivo real es una sola hoja de 187 filas con todas las secciones clínicas esperadas (heredofamiliares, antecedentes, inmunizaciones, gineco-obstétrico, exploración física por 13 regiones incluida carta dental, diagnóstico, plan, resultado). Queda abierto dentro de este punto: carta dental (ver #15) y el sistema de numeración dental.
- **#4 — Definición de "INCLUSIÓN"**: confirmado contra 3 reportes reales independientes que el examen tiene 4 resultados con clave numérica propia: `APTO=15`, `NO_APTO=30`, `CONDICIONADO=45`, `INCLUSION=60` (INCLUSIÓN no es sinónimo de CONDICIONADO). Queda abierto: typo "APTO 1945" en la plantilla base (ver #12) y el protocolo operativo de qué hace RRHH ante cada resultado.
- **#11 — Distinción CUENTA vs. AREA**: son dos catálogos independientes por diseño. CUENTA = cliente externo al que Onest presta servicio; AREA = departamento interno de Onest. No se fusionan aunque 5 nombres coincidan entre ambos.
- **#14 — Alcance de inventario médico general**: descartado explícitamente por el usuario. Inventario de medicamentos/equipo médico general queda fuera de alcance. El inventario de antidoping (kits de prueba) sí se mantiene como parte del bloqueador #3.

## Abiertos o parciales

- **#2 — Catálogo de diagnósticos** (Médico Jefe): confirmado que la captura real hoy es texto libre, no ICD10 cerrado. Falta decidir si debe normalizarse a un catálogo (necesario para cualquier reporte de "top diagnósticos").
- **#3 — Protocolo de antidoping/alcoholimetría** (Gerente SO): estructura de datos confirmada (sustancias, resultado, inventario de insumos separado del resultado). Falta el protocolo clínico: cuándo se aplica, a quién, manejo de positivos.
- **#5 — Reglas de NSS** (RRHH): sin confirmar si el NSS es único o puede repetirse entre empresas/predios (empleado multi-predio).
- **#6 — Origen de datos de incapacidades** (Gerente SO): confirmada la separación IMSS/interna y el desglose de costos por causa. Falta confirmar si hay integración automatizada con IMSS o es captura manual.
- **#7 — Proceso de accidentes laborales** (Gerente SO): confirmada la estructura de datos (tipo de riesgo LABORAL/TRAYECTO, catálogo de causas RT, status de calificación, SDI). Falta el flujo de investigación: quién califica, con qué criterio, plazos.
- **#8 — Catálogo de restricciones médicas** (Médico Jefe): ningún reporte real trae un catálogo de restricciones (ej. "no cargar más de X kg"). Sigue sin proporcionarse.
- **#9 — Matriz de permisos y confidencialidad** (Admin + Médico): sin definir alcance de lectura por rol (médico/gerente/auditor) y si el corte de acceso debe ser también por CUENTA (cliente externo), no solo por predio.
- **#10 — Migración histórica** (Stakeholder): sin decidir si el alcance inicial incluye datos históricos o no.
- **#12 — Typo "APTO 1945"** en la plantilla base `EXAMEN MEDICO.xlsx` (debería decir "APTO 45", clave 45 = CONDICIONADO). Confirmar si es error de plantilla o indicio de una quinta clave.
- **#13 — Campo "SALIDA" ambiguo** en antecedentes laborales: probablemente el motivo de baja de un empleo anterior del candidato, no el resultado del examen actual (que vive en su propia sección con clave 15/30/45/60). Confirmar interpretación.
- **#15 — Sistema de numeración de carta dental** (Médico Jefe): ✅ **RESUELTO (2026-08-10), no requiere decisión de negocio.** Verificado con datos reales de `SERV_MED_DIENTES` (20 filas de `ONEWMS_QA`, compartidas por el usuario) y contra el HTML del formulario original (`php-old/view/content/formsEFis/EFis.html`): el sistema real **nunca implementó** la clasificación C/A/E/P/X (caries/amalgama/endodoncia/prótesis/ausencia) que aparece impresa en `EXAMEN MEDICO.xlsx` — cada diente siempre fue un `<input type="text">` de texto libre, y en la práctica casi todos los registros reales solo tienen el placeholder por defecto `"sin observaciones"`/`"SIN OBSERVACIONES"` (ninguna nota clínica real en la muestra). La numeración de piezas sí es FDI/ISO de dos dígitos (11-18/21-28/31-38/41-48, confirmado en `docs/contextoWS.txt:4755-4810`). **Decisión tomada**: no se construye un selector C/A/E/P/X — sería agregar funcionalidad que el sistema real nunca tuvo, sin ninguna fuente (ni php-old ni Oracle) que la respalde. El catálogo Java se queda como texto libre por diente, fiel al sistema real.
  - **Hallazgo adicional en el mismo análisis**: el campo del diente 21 se llama `DIENTE_2` en el formulario legacy (`php-old/app/app.php:639`, confirmado también en el HTML del form) — **no** `DIENTE_21`. Pero el procedimiento PL/SQL que guarda (`docs/contextoWS.txt:4772`) lee el JSON en el path `SERV_MED_DIENTES.DIENTE_21`, y la columna real de la tabla es `DIENTE_21` (no existe columna `DIENTE_2`). Es decir: **el propio legacy PHP nunca guardó correctamente el diente 21** — envía una clave que el WS no lee. Los datos reales lo confirman: `DIENTE_21` está vacío en el 100% de las filas. El catálogo Java (corregido hoy a `DIENTE_21`) ya no repite este bug del legacy — es una mejora real sobre el sistema actual en producción, no solo fidelidad al PHP.
  - **Confirmación con la tabla completa (2026-08-10, 3,208 registros reales de `SERV_MED_DIENTES`)**: 2,136 filas (67%) completamente vacías, 777 con el placeholder `"sin observaciones"`, 212 con `"SI"` repetido, y **cero coincidencias** para cualquier término clínico dental real (caries, amalgama, endodoncia, prótesis, corona, extracción, fractura, dolor) en todo el archivo. Los pocos códigos de una letra que aparecen (C/A/P/X/O) están repetidos idénticos en los 6+ dientes de la misma fila, sin variar por pieza — no se ven como una exploración clínica real, sino como valores de prueba. Confirma sin ambigüedad que esta sección nunca se usó para documentación clínica dental real en producción.
- **#16 — Uso clínico real de componentes de dashboard tipo heatmap/benchmark/banda de control**: quedó sin especificar qué dato real y en qué sección del dashboard deben mostrarse (aplica solo si se construye un dashboard de morbilidad en Java más adelante).
- **#17 — Diccionario de siglas del Pretest**: el cuestionario de síntomas previo al examen en el legacy usa siglas sin diccionario (LHOP, SUAA, SAFOPH, TALMED, etc.). No se puede construir/completar esa pantalla sin que el equipo médico confirme el significado de cada sigla — aplica directamente al módulo Pretest ya existente en el portal Java (`catalog/pretest/`).

## Hallazgos adicionales al revisar Examen Médico contra el WS real (2026-08-10)

Durante el pulido de U07 se verificó código contra `docs/contextoWS.txt` y aparecieron datos nuevos sobre puntos ya listados arriba:

- **`AGENCIA`** (campo que js-version proponía capturar: GLI/Orlamex/Valle Lerma/Onest/Otro): el único rastro en el WS real es un valor **hardcodeado** (`'sin agencia'`) dentro de otro endpoint de solo lectura — no es un campo real capturable hoy en `Servcio/Medico`. No se agregó al catálogo Java porque no hay dónde guardarlo todavía.
- **Dictamen del examen** (Apto/No apto/Apto condicionado/Apto restringido): verificado **correcto** contra la tabla real `SERV_MED_RESULTADO_EXAMEN` (4 columnas booleanas, coinciden 1:1 con lo ya implementado en Java). El "INCLUSIÓN(60)" que veía js-version en los reportes de Excel es un concepto aparte — no vive en esta tabla, sigue sin explicación, no bloquea el catálogo actual.
- **Campo "SALIDA" ambiguo** (punto #13 de este checklist): **confirmado** contra `docs/contextoWS.txt:4900,4918-4921` — es `AÑO_SALIDA`, dentro de `SERV_MED_DET_ANT_LABORALES` (un trabajo previo del candidato), no el resultado del examen actual. Ya no es ambiguo.
- **Antecedentes laborales**: sección "resumen" (edad al iniciar a laborar, cuántos trabajos, pensión IMSS) agregada al catálogo Java. La lista de trabajos previos (empresa, puesto, turno, años, riesgos, EPP) también se agregó como tabla repetible en la UI, pero **sin precargar datos existentes** — el path de lectura de ese arreglo no está confirmado contra el WS real (el código fuente mezcla dos rutas JSON distintas para el mismo arreglo, ver comentario en `BiowsExamenClient.guardar()`). Solo captura trabajos nuevos en la sesión actual; verificar contra un ambiente real antes de confiar en el guardado.
  - **Verificado con datos reales (2026-08-10)**: la sección "resumen" **sí funciona** — 3,208/3,208 filas de `SERV_MED_ANT_LABORALES` tienen `CANTIDAD_TRABAJOS`/`PENSION`, 3,207/3,208 tienen `EDAD_INICIO_LABORAL`. Las claves en minúscula del catálogo Java son correctas.
  - La lista de "trabajos previos", en cambio, está **confirmada rota en el propio legacy**: `SERV_MED_DET_ANT_LABORALES` tiene 51,730 filas, pero **cero** con contenido en `GIRO_NEGOCIO`/`NOMBRE_PUESTO`/`NO_TRABAJO`/`DESCRIPCION_TRABAJO`/`OBSERVACIONES` (todo NULL) — el legacy PHP tampoco logró nunca guardar esto (probablemente porque, al no coincidir `NO_TRABAJO`, cada guardado inserta una fila nueva en vez de actualizar, de ahí el volumen). No hay dato real que se pueda perder, pero tampoco hay forma de confirmar qué estructura de payload SÍ funciona — nadie lo ha logrado nunca en producción. Se agregó una advertencia visible en la UI (`examen-shell.html`) y hay que probar contra el WS real antes de confiar en el guardado.
- **Bug corregido**: `DIENTE_2` → `DIENTE_21` en el catálogo de carta dental (mismo patrón que el bug de `SABIN` corregido antes) — confirmado contra `docs/contextoWS.txt:4772,4796,4808`.

## Notas técnicas heredadas (ya no aplican al portal Java, se dejan por trazabilidad)

`js-version` dejó documentados dos problemas de su propio schema PostgreSQL (sintaxis MySQL inválida en `001_schema_base.sql`, vistas de `002_views_morbilidad.sql` con columnas que no coinciden con `003_schema_dimensiones_reales.sql`). No aplican al portal Java, que no tiene base de datos propia — todo dato viene de WS ORDS sobre Oracle `ONEWMS_QA`. Se mencionan solo para no perder el contexto si se recupera el schema de `js-version/db/migrations/` como referencia de modelado a futuro.

## Cómo usar este documento

Antes de empezar a construir en Java cualquiera de estos módulos nuevos (dashboard de morbilidad, antidoping, accidentes de trabajo como entidad propia, maternidad como módulo propio, restricciones médicas, o completar Pretest/carta dental), verificar aquí si el bloqueador correspondiente sigue abierto. Si sigue abierto, no asumir una resolución razonable — preguntar explícitamente al responsable indicado o al usuario, según la regla de honestidad ya establecida para este proyecto (no inventar catálogos, reglas de negocio ni valores de ejemplo).
